# R1.2a-1：16GB Windows 本地转换可行性验证

日期：2026-11-01。仅本机；没有云端/其他机器/新增硬件；没有真实转换、F1训练或Git写操作。

## 决策

内存与磁盘方面，发现了适合当前机器的受限方案，并已通过合成验证，
不再把高内存机器作为唯一选项。但不能据此声明真实包已经可以安全完整转换：
目前只验证了真实包的有界头部，后续数组/标量和整个pickle的白名单兼容性未知。
最小阻塞是完整结构尚未核验，不是16GB物理内存必然不足。

推荐两阶段：有界zstd解压至本地临时文件 → 严格操作码/NumPy状态校验和数组段索引 →
只复制五数组的[0,2918)字节至NPY → 回读校验 → 同卷独占发布目录。
本轮工具故意限制压缩输入<=64 MiB、解压文件<=128 MiB，拒绝真实data.z。
下一步建议先批准真实包的限内存完整结构审计（不发布训练数据）；全部结构通过后，
再批准真实转换及生产入口的资源监控。不能直接把本轮探针当作已验收的生产转换器。

## 2. 实际格式证据和安全边界

读取真实文件外层7字节、末尾2字节及最多1 MiB压缩前缀，zstd reader只请求192字节解压头。
其中pickletools.genops只接收这个有界内存buffer，不传真实文件句柄；未执行pickle.load/loads。
解码器可能预取有限压缩数据，但未遍历真实后部，更没有解释标签。

- 外层：protocol5，BINBYTES精确长度3,250,274,519，尾部MEMOIZE/STOP，文件长度吻合。
- zstd：窗口2 MiB，content_size约8.47 GiB，checksum=false。
- 内层：protocol4；首个FRAME长度147；NumPy `_reconstruct`、ndarray、dtype f4、
  dtype状态小端、shape=(3603,5282,99)、fortran_order=False。
- 首个数组使用BINBYTES8，声明7,536,294,216字节，恰为3603×5282×99×4。
  该数组段起点可由操作码长度计算为解压文件offset 167，完全不需要字节搜索。
- 未核实后续数组是否同样为C顺序连续数值段、是否有额外键/NumPy标量/其他opcode。

查看了本机Python3.13 pickle.py和pickletools.py的实现：load_binbytes8/read_bytes8
会按声明长度调用read(n)。因此把pickletools.genops直接用于整个真实流，也可能尝试读取7GB载荷。
本轮正式索引器自行按操作码长度seek，不使用pickletools处理大文件。

现有src/io.py先保存约3.03 GiB压缩bytes，再生成约8.47 GiB raw，
pickle.loads又创建数组/临时bytes；按生命周期可能同时需要20 GiB以上，瞬时复制可能更多。
bytes(obj)对原本bytes通常不复制，对bytearray等则可能复制；不能笼统说它每次复制。
原读取路径未执行或修改。

## 3. 探针实现

src/numpy_pickle_probe.py不是通用pickle解释器，只识别平坦赛题dict的数值ndarray序列化子集：

- 内层只接受protocol4，外层只接受实测protocol5/BINBYTES/尾部格式。
- STACK_GLOBAL只可引用NumPy ndarray、dtype、两个已知模块名下的_reconstruct；
  REDUCE和BUILD只进行符号/状态检查，绝不导入或调用这些对象。
- 数值dtype白名单，不接受object、结构化dtype、任意类、Fortran布局、外部缓冲或额外未知键。
- shape、dtype、二进制长度必须一致；frame边界、文件边界、memo索引、STOP、时间切分、
  根dict结构和数组间不重叠均须通过；不能跳过未知opcode或未知对象继续生成数据。
- opcode<=4096、stack<=256、memo<=512、元数据累计<=64 KiB、单字段<=128 bytes、frame<=1 MiB。
- 所有数组段只记录offset/length；完整结构通过之前不创建最终NPY目录。
- 复制训练前缀时每块<=1 MiB，原始字节不改精度、不重排、不重编码NaN或有符号零。
  y2、官方valid/test部分不提取、不解释；其位置在索引阶段只seek跳过。
- 原始位置编号写入stock_ids/feature_ids，绑定源包hash；不是推断出的股票代码或特征含义。
- 写NPY同时计算与R1.1相同的逐行摘要，再从磁盘回读重算并核验文件hash。
  源压缩文件转换前后hash须相同，输出manifest最后完成。

解压临时文件如在下一阶段获准生成，会包含整包的原始序列化字节，包括未解释的标签字节。
这与提取测试标签数值是两回事，但仍需在批准范围内明确；本轮没有生成这种真实临时文件。
源包无zstd checksum：语法/长度错误可检测，任意载荷位翻转未必改变语法，不能承诺一律发现。
需要与可信来源hash比对才有外部完整性依据；本轮自算hash主要检测转换期间源文件变化。

### 中断与发布

使用同目录独占随机工作区，包含owner.json、inner.pickle和package；最终目录在全部校验前不存在。
所有文件flush/fsync后，Windows同卷目录rename发布；目标已存在则报错，绝不覆盖。
普通异常/KeyboardInterrupt清理本次拥有的工作区；硬退出留下未发布目录，
cleanup_owned核对位置/所有权记录、拒绝链接后才允许清理。重跑创建新的工作区，不能复用半成品。
这验证的是进程中断与目录可见性的原子性，不宣称Windows断电/磁盘故障后的绝对持久性。

## 4. 内存预算：算法约束与实测

| 阶段 | 数据缓冲/资源特征 |
|---|---|
| 外层/压缩头检查 | 几十字节，输入文件不整体读取 |
| zstd解压 | 输出块1 MiB；允许窗口<=4 MiB，真实窗口2 MiB；另有库内部缓冲 |
| pickle索引 | 元数据<=64 KiB和有限对象表；数组载荷seek，不分配数组 |
| NPY写出/逐行hash | 块<=1 MiB，单行也可分块；不把整行或数组一次读入 |
| 文件SHA256 | 复用项目8 MiB分块函数；赋值交叠时可能同时存活两块，约16 MiB |
| 发布前回读 | 与写出同样分块；不调用全数组np.load或mmap扫描 |
| Python/NumPy/SciPy | 需要独立计入解释器、库、线程池，不从缓冲大小推算为零 |

转换工具不做BLAS运算，因此在其进程导入NumPy之前把BLAS/OMP线程限制为1；
没有更改模型训练默认配置。初测未限制线程时，导入后Private Bytes约1.51 GiB；
限制后约68 MiB，说明库初始化开销不能忽略。

最终合成测量在独立子进程内进行，生成数据的过程不混入转换峰值。
Windows GetProcessMemoryInfo提供进程生命周期峰值工作集和峰值提交量：

| 合成规模 | 解压文件 | 新NPY目录 | 临时+输出峰值 | 峰值工作集 | 峰值提交量 |
|---|---:|---:|---:|---:|---:|
| 48×256×99数值特征 | 5.602 MiB | 4.401 MiB | 10.004 MiB | 102.58 MiB | 80.96 MiB |
| 384×256×99数值特征 | 44.813 MiB | 35.531 MiB | 80.344 MiB | 106.14 MiB | 84.61 MiB |

两组还含9列int64类别、两个bool mask、y1/y2 float32及切分标量，训练前缀约80%。
磁盘峰值由同一时刻raw和输出目录的实际文件长度求和，另有很小的owner/fixture记录，
不包含原有合成输入及NTFS簇/系统缓存开销。
含输入分别约14.48/116.10 MiB。旧测量保留，新测量使用独占新目录。
原始测量文件：outputs/r12a1_probe_48_verified/measurement.json、
outputs/r12a1_probe_384_verified/measurement.json。

证据支持内存主要取决于缓冲而非整个数据量，但44.8 MiB不是8.47 GiB的实际峰值证明。
未来生产执行建议进程工作集/提交量各设512 MiB停止阈值、系统可用内存至少1 GiB，
并测量系统余量；这些生产监控尚未实现，不可把建议写成已具备的保护。
没有修改页面文件或依赖整包虚拟内存分配。PageFaultCount含软缺页，不等于磁盘交换，
未测量系统全局硬缺页，不能宣称全机完全零换页。

## 5. 合成验收与兼容性

新增13项测试：

1. 数值、dtype、shape、股票/时间/特征顺序、NaN/Inf/负零字节一致，以及PrefixStore直接读取兼容。
2. 大端float64字节保持。
3. 超过1 MiB的单行分块复制及无checksum的zstd帧。
4. 发布前发现输出字节损坏。
5. 索引阶段用读保护器证明不读取数组载荷。
6. 合成BINBYTES升级BINBYTES8，验证64位长度头和无frame大字节段定位。
7. 截断、错误frame跨界、尾部垃圾、未知opcode、巨额声明长度拒绝。
8. 任意global、object/Fortran数组、未知键、错误时间边界、数组别名拒绝。
9. 压缩损坏/校验和错误、外层截断/尾随数据拒绝。
10. KeyboardInterrupt在不同阶段的清理及重跑。
11. 发布前目录不可见、目标竞争出现时不覆盖。
12. 独立进程硬退出、遗留工作区检查/清理及重新执行。
13. 真实规模输入和巨额frame受到探针硬上限阻止。

58项unittest通过，加原有7项覆盖度/融合测试，共65项。训练相关回归仅使用微型合成数据。
真实后部结构、全量耗时、全量磁盘故障和完整转换内存峰值均未验证。

不需要修改prefix_store接口：探针输出同一prefix-store-v1/oof-prefix-v1协议，
增加conversion说明不影响现有读者。绕开export_prefix的全数组映射，仅是转换内部实现选择。
旧的src/io.py、prefix_store、fold_runner、配置、缓存和历史产物全部保持不变。

## 6. 下一步批准范围

可以考虑批准下一阶段的本地真实包完整结构审计，条件是先补齐生产资源停止阈值，
仍然禁止原pickle完整加载和任意对象执行，且只落地临时字节文件与结构清单，不发布训练前缀。
真实结构若与白名单完全一致，再批准字节复制/回读/原子发布；若不一致，报告具体opcode/对象，
停止并针对最小差异补测试，不通过宽松跳过或通用Unpickler兜底。
这一路径不要求外部高内存机器，但本轮不能无条件批准“真实转换已安全可运行”。

新增文件仅为src/numpy_pickle_probe.py、scripts/probe_numpy_conversion.py、
tests/test_numpy_pickle_probe.py和本报告。合成测量产物保存在新建且被忽略的outputs子目录。

最终保护核验：开始快照中的160个已有文件逐字节hash均不变；HEAD、索引字节、
暂存diff均不变，仍为88个暂存文件。仅新增上述4个未跟踪文件；AST、空白检查和
git diff --check通过。补充时间边界检查后新增13项测试再次全部通过。
